# Текстовая документация проекта

## 1. Краткое описание архитектуры

Проект реализует прототип автоматизации сервисного центра на базе Битрикс24.

Основная логика вынесена в кастомный модуль:

```text
/local/modules/sharov.servicecenter
```

Дополнительно используются компоненты, AJAX/API-файлы, JS-скрипты и административные tools-файлы для настройки и проверки.

### Основные папки проекта

```text
/local/modules/sharov.servicecenter/
```

Кастомный модуль сервисного центра. Содержит бизнес-логику проекта: обработчики CRM-событий, сервисы работы с гаражом, закупками, остатками, уведомлениями и агентами.

```text
/local/components/sharov/servicecenter.garage/
```

Компонент вкладки “Гараж” в карточке клиента. Отвечает за отображение автомобилей клиента, добавление, редактирование, удаление автомобилей и просмотр истории обращений.

```text
/local/tools/
```

Служебные и диагностические файлы. Используются администратором для настройки, проверки API, проверки остатков, регистрации агентов и тестирования логики. Обычные пользователи с этими файлами не работают.

```text
/local/js/sharov.servicecenter/
```

JavaScript-файлы для доработки интерфейса Битрикс24: выбор автомобиля в сделке, выбор механика, выбор запчастей, фильтрация товаров сделки и оформление пользовательских полей.

```text
/local/php_interface/init.php
```

Файл подключения обработчиков событий, JS-скриптов и кастомной логики проекта.

## 2. Основные файлы решения

### Модуль сервисного центра

```text
/local/modules/sharov.servicecenter/lib/Crm/DealEventHandler.php
```

Обработчик событий CRM-сделок. Используется для контроля незакрытых заказ-нарядов. При создании или изменении сделки проверяет, есть ли уже открытый заказ-наряд по выбранному автомобилю. Если есть, запрещает создание новой сделки и отправляет уведомление ответственному.

```text
/local/modules/sharov.servicecenter/lib/Service/PurchaseRequestService.php
```

Сервис работы с заявками на закупку. Отвечает за создание автоматических и ручных заявок, обработку одобрения, отказа, перевод стадий, защиту от повторной обработки и увеличение остатков.

```text
/local/modules/sharov.servicecenter/lib/Service/CatalogStockService.php
```

Сервис работы с остатками товаров каталога. Используется для обновления количества запчастей в каталоге Битрикс24.

```text
/local/modules/sharov.servicecenter/lib/Service/NotificationService.php
```

Сервис системных уведомлений. Отправляет уведомления закупщику, инициатору заявки и ответственному по сделке.

```text
/local/modules/sharov.servicecenter/lib/Service/ServicePartProvider.php
```

Сервис получения списка запчастей. Запчастями считаются товары, находящиеся в разделе каталога “Запчасти сервисного центра”. Сервис получает список таких товаров и их остатки.

```text
/local/modules/sharov.servicecenter/lib/Agent/StockSyncAgent.php
```

Агент синхронизации остатков запчастей. Запускается по расписанию и обновляет остатки запчастей из внешнего сервиса.

```text
/local/modules/sharov.servicecenter/lib/Agent/PurchaseRequestAgent.php
```

Агент обработки ручных заявок на закупку. Обрабатывает заявки, переведённые в стадии “Одобрено” или “Отклонено”.

Служебный файл для создания раздела “Запчасти сервисного центра” в основном каталоге товаров.

/local/tools/sharov_servicecenter_register_stock_agent.php

Файл регистрации агента синхронизации остатков.

/local/tools/sharov_servicecenter_process_purchase_requests.php

```text
/local/js/sharov.servicecenter/deal-service-selects.js

/local/js/sharov.servicecenter/purchase-request-selects.js

/local/js/sharov.servicecenter/deal-product-parts-filter.js
```

Скрипт фильтрации товаров в сделке. В стандартном селекторе товаров Битрикс24 скрывает товары и услуги, которые не относятся к разделу “Запчасти сервисного центра”.

## 3. Используемые сущности

### 3.1. Контакты CRM

Клиенты сервисного центра хранятся в стандартной сущности Битрикс24:

```text
CRM → Контакты
```

В карточку контакта добавлена вкладка:

```text
Гараж
```

Во вкладке отображаются автомобили клиента.

---

### 3.2. Автомобили клиента

Автомобили хранятся в отдельной кастомной таблице:

```text
b_sharov_sc_car
```

Основные поля таблицы:

```text
ID
CONTACT_ID
BRAND
MODEL
LICENSE_PLATE
YEAR
COLOR
MILEAGE
VIN
DATE_CREATE
DATE_UPDATE
```

Связь автомобиля с клиентом выполняется через поле:

```text
CONTACT_ID
```

Это позволяет хранить несколько автомобилей у одного клиента.

---

### 3.3. CRM-сделки

Сервисные заказ-наряды реализованы через стандартные CRM-сделки.

В сделках используются пользовательские поля:

```text
UF_CRM_SC_CAR_ID              — автомобиль сервисного центра
UF_CRM_SC_MILEAGE_IN          — пробег при приёмке
UF_CRM_SC_COMPLAINT           — жалоба клиента
UF_CRM_SC_MECHANIC_ID         — механик
UF_CRM_SC_IS_SERVICE_ORDER    — признак “Сервисный заказ-наряд”
```

Поле `UF_CRM_SC_CAR_ID` связывает сделку с автомобилем из таблицы `b_sharov_sc_car`.

---

### 3.4. Запчасти

Запчасти хранятся в стандартном каталоге товаров Битрикс24.

Для определения запчастей используется раздел каталога:

```text
Запчасти сервисного центра
```

Если товар находится в этом разделе, он считается запчастью сервисного центра.

Такие товары:

```text
- появляются в списке запчастей;
- доступны для выбора в заявке на закупку;
- участвуют в синхронизации остатков;
- могут добавляться в товарные строки сделки;
- участвуют в автозакупке при отсутствии остатка.
```

---

### 3.5. Заявки на закупку

Заявки на закупку реализованы через смарт-процесс CRM:

```text
Заявка на закупку
```

В заявке используются поля:

```text
Запчасть
Количество
Инициатор заявки
Согласующий
Причина отказа
Автоматическая заявка
```

Основные стадии:

```text
На согласовании
Одобрено
Выполнено
Отклонено
```

---

### 3.6. Таблица защиты от повторной закупки

Для защиты от повторного выполнения закупки используется таблица:

```text
sharov_sc_purchase_processed
```

Она хранит статус обработки заявки:

```text
PROCESSING
APPROVED
REJECTED
AUTO_DONE
```

Это нужно, чтобы агент не увеличивал остатки повторно при повторном запуске.

## 4. Технические нюансы

### 4.1. Контроль незакрытых заказов

При создании нового сервисного заказ-наряда система проверяет, есть ли уже открытая сделка по тому же автомобилю.

Проверяются:

```text
- выбранный автомобиль;
- признак “Сервисный заказ-наряд”;
- стадия сделки.
```

Если по автомобилю уже есть незакрытый заказ-наряд:

```text
- создание новой сделки запрещается;
- пользователь получает ошибку;
- ответственному отправляется уведомление.
```

Если предыдущая сделка находится в финальной стадии, создание нового заказ-наряда разрешается.

Обычные сделки без признака “Сервисный заказ-наряд” не блокируются.

---

### 4.2. Гараж клиента

Гараж реализован отдельным компонентом в карточке контакта.

Во вкладке “Гараж” пользователь может:

```text
- посмотреть список автомобилей клиента;
- добавить автомобиль;
- изменить автомобиль;
- удалить автомобиль, если по нему нет сделок;
- открыть историю обращений по автомобилю.
```

Если по автомобилю уже есть сделки, удаление запрещается. Это сделано для защиты истории обслуживания.

---

### 4.3. История обращений по автомобилю

История строится по CRM-сделкам, связанным с автомобилем через поле:

```text
UF_CRM_SC_CAR_ID
```

В истории отображаются:

```text
- название сделки;
- дата создания;
- стадия;
- ответственный;
- сумма;
- список запчастей.
```

Стадия отображается пользователю названием, а не техническим кодом. Ответственный отображается ФИО, а не ID пользователя.

---

### 4.4. Выбор автомобиля в сделке

В карточке сделки пользователь выбирает клиента. После выбора клиента система подгружает список его автомобилей.

Пользователь видит понятный список:

```text
BMW X5 — A123AA777, 2022, Серый
Lada Vesta — Т111ТТ778, 2023, Белый
```

В сделку сохраняется технический ID автомобиля, но в интерфейсе отображается нормальное название.

---

### 4.5. Выбор механика

Поле механика в сделке работает через пользовательский список. Пользователь выбирает механика из списка сотрудников, а не вводит ID вручную.

---

### 4.6. Фильтрация товаров в сделке

Стандартный селектор товаров Битрикс24 показывает все товары и услуги каталога. Для сервисного центра это неудобно, поэтому добавлен JS-фильтр:

```text
/local/js/sharov.servicecenter/deal-product-parts-filter.js
```

Он оставляет в списке только товары из раздела:

```text
Запчасти сервисного центра
```

Это не позволяет пользователю случайно выбрать услугу или посторонний товар вместо запчасти.

---

### 4.7. Синхронизация остатков

Остатки запчастей обновляются агентом:

```text
\Sharov\ServiceCenter\Agent\StockSyncAgent::run();
```

Агент запускается по расписанию. Для рабочего режима используется интервал:

```text
86400 секунд
```

То есть один раз в сутки.

Логика:

```text
1. Получить список запчастей.
2. Для каждой запчасти запросить внешний сервис.
3. Внешний сервис возвращает текущее количество.
4. Если количество больше 0 — обновить остаток в каталоге.
5. Если количество равно 0 — выполнить автозакупку.
```

Для демонстрации в качестве внешнего сервиса может использоваться random.org, который возвращает число от 0 до 10.

---

### 4.8. Автоматическая закупка

Если внешний сервис возвращает количество:

```text
0
```

система выполняет автоматическую закупку:

```text
1. Создаёт заявку на закупку 10 единиц.
2. Уведомляет закупщика.
3. Устанавливает остаток товара в 10.
4. Переводит заявку в статус “Выполнено”.
```

Автоматическая закупка не требует ручного согласования, потому что по ТЗ она выполняется автоматически при отсутствии запчасти.

---

### 4.9. Ручная заявка на закупку

Сотрудник может вручную создать заявку на закупку.

В заявке выбираются:

```text
- запчасть;
- количество;
- инициатор;
- согласующий.
```

При одобрении закупщиком:

```text
- остаток товара увеличивается;
- заявка переходит в статус “Выполнено”;
- инициатор получает уведомление об успешной закупке.
```

При отказе:

```text
- причина отказа обязательна;
- остаток товара не меняется;
- заявка остаётся в статусе “Отклонено”;
- инициатор получает уведомление с причиной отказа.
```

Если причина отказа не указана, система возвращает заявку обратно на согласование.

---

### 4.10. Уведомления

В проекте используются системные уведомления Битрикс24.

Реализованы уведомления:

```text
- ответственному о наличии открытого заказ-наряда по автомобилю;
- закупщику об автоматической закупке;
- инициатору об успешной ручной закупке;
- инициатору об отказе с причиной.
```

---

### 4.11. Обработка исключений

В API и сервисах используется обработка исключений через `try/catch`.

При ошибке API возвращает JSON:

```json
{
  "success": false,
  "error": "Описание ошибки"
}
```

При успешном выполнении API возвращает:

```json
{
  "success": true,
  "data": {}
}
```

Такой подход используется в гараже, списках запчастей, заявках на закупку и AJAX-обработчиках.

---

### 4.12. Защита от повторной обработки заявок

Агент обработки закупок может запускаться повторно. Чтобы заявка не увеличивала остаток несколько раз, используется таблица:

```text
sharov_sc_purchase_processed
```

Перед выполнением закупки заявка помечается как:

```text
PROCESSING
```

После успешной обработки:

```text
APPROVED
```

Для автоматических закупок:

```text
AUTO_DONE
```

Это защищает систему от повторного увеличения количества запчастей.

---

### 4.13. Права доступа

В проекте используются роли:

```text
Механик сервисного центра
Менеджер сервисного центра
Закупщик сервисного центра
Начальник отдела закупок
Директор сервисного центра
```

Менеджер работает с клиентами, гаражом и сделками.

Механик видит назначенные ему заказ-наряды.

Закупщик работает с заявками на закупку.

Директор имеет полный доступ.

---

## 5. Интеграции

### 5.1. Внешний сервис остатков

Система получает текущее количество запчастей из внешнего сервиса.

Для демонстрации может использоваться:

```text
https://www.random.org/integers/?num=1&min=0&max=10&col=1&base=10&format=plain&rnd=new
```

Сервис возвращает число от 0 до 10.

---

### 5.2. API гаража

Для интеграции с внешними системами реализован JSON API гаража:

```text
/local/tools/sharov_servicecenter_garage_api.php?action=list&contactId=...
```

Получение списка автомобилей клиента.

```text
/local/tools/sharov_servicecenter_garage_api.php?action=history&carId=...&contactId=...
```

Получение истории обращений по автомобилю.

---

## 6. Итог

В проекте реализованы основные требования ТЗ:

```text
- CRM-воронка сервисного обслуживания;
- гараж клиента;
- отдельное хранение автомобилей;
- история обращений по автомобилю;
- контроль незакрытых заказ-нарядов;
- запчасти в каталоге товаров Битрикс24;
- ежедневная синхронизация остатков;
- автоматическая закупка при отсутствии запчасти;
- ручные заявки на закупку;
- уведомления;
- роли и права доступа.
```
